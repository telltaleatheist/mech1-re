# Phase 2: content out

The goal: the game reads no executable at play time. The original's creative
content comes from a story file the game writes once from the player's own
exes; everything else it needs is ours, in data files in this repo, or is
code. Copy protection, disk prompts and the DOS launcher go. Traces stay 7
of 7, except where our own wording changes a screen, and every such snap is
re-recorded and noted in the same commit.

The scoping report (mw3-re, `mw1/research/original-rebuild-scoping.md`,
sections 3, 4 and 7) is the brief. `INVENTORY.md` lists every item
`src/Original/Memory` holds today with its group (generated by
`tools/phase2/inventory.py`; names and native offsets only).

**Extracted** (the scoping report's items 1 to 3; art, models, maps and sound
files stay in the install and are read in place):
- the story: the event script and its text bank (MW_MAIN 1AA5), the six
  story-planet pools and their selectors;
- narrative text: the intro's seven panels, contract narratives and mission
  descriptions, the per-House after-action texts, the settlement
  explanations, the Dark Wing texts, the uneventful-deployment text, mission
  titles;
- names: pilot definitions (names, portrait ids, dialogue), planet records
  (names and descriptions), the commander's default name (both exes), mech
  display names as MW1 spells them (campaign and combat), House contract
  names and refusals;
- MW1's music sequence table and the AdLib default instruments (sound design).

**Ours, UI words.** Every menu and panel label, heading, caption, cockpit
lamp and inspection label, the retreat question, ZOOM/AUTO/PAUSED, month
names, ammo family and damage tier names, and every system message ("no
contracts", "insufficient funds", save and load errors, full roster).
These are written fresh, in our wording: MW1's own words never enter the
repo, so a label is never transcribed, only its meaning kept. Each change
re-records the snaps that show it.

**Ours, layout.** Panel descriptors (x, y, width, line count, border,
spacing, background), menu records (position, picture, links), row origins,
diagram anchors, colour tables, the DropShip and mech-complex animation
frames. Numbers, transcribed: they are what makes a screen line up.

**Ours, rules.** Prices and multipliers, repair and ammo tables, pilot pay
and skill tiers, market generation, mission force weights and payment rolls,
House policies, combat damage tiers, hit location and cluster rows, heat and
transfer tables, mech templates and weapon definitions, AI offsets. Numbers,
transcribed from the original; data we own and may tune. A test compares
each table with the player's exe when one is present (the import table's
hashes, below, do this for free).

**Ours, new campaign.** The initial values of MW_MAIN's save block
(DS:0448..0B5F): starting funds, date, commander age, House standings,
roster and market at start. Today the port reads them from MW_MAIN's data
segment; they become one file, `new_campaign.json`, in the save format's
field names.

**Dropped.** Copy protection (pictures, callsigns, answers, prompt),
disk-swap prompts (campaign, combat, save), the DOS launcher (MW.EXE's
strings, memory tier, graphics prompt, exit codes), Tandy and Hercules
tables, the startup error text. Slice 1 below.

**Code.** Runtime state (zero at start or set before use), the EGA and
polygon renderer's tables, the MIDI/MPU/AdLib driver state, input and
timer state. They stay as code; Phase 3 gives them owners.

## 2. The file formats

Both follow Inception's shape (crescent-hawks-rebuild `docs/import.md`):
plain JSON with named fields, one place for every ID, readable and moddable.

**Ours, in the repo** (`data/`, installed beside the program):

    data/text/interface.json   {"texts": [{"id": "market.buy", "text": "Buy"}, ...]}
    data/ui/campaign.json      {"panels": {"market.list": {"x": 8, "y": 24, "width": 200,
                                 "lines": 13, "border": 1, "spacing": 2, "background": 7}},
                                "menus": {"hub": [{"x": .., "y": .., "picture": 1,
                                 "links": [5, 1, 255, 3], "text": "hub.contracts"}]}}
    data/rules/market.json     {"unit_base_prices": [...], "price_tier_multipliers": [...]}
    data/rules/new_campaign.json  {"funds": ..., "year": ..., "house_standings": [...]}

Text ids are dotted (`screen.item`). A menu row's label is a text id, not a
string. Arrays keep the original's order and length, so an index means what
it meant in the exe; each array's length is checked at load.

**Extracted, in the player's data folder** (`<write dir>/story/`):

    story/import.json      {"import_version": 1, "sources": {"MW_MAIN.EXE": "<sha256>",
                            "BTECH.EXE": "<sha256>", "MW.EXE": "<sha256>"},
                            "revision": "1990-01-22", "table_sha256": "..."}
    story/text.json        {"texts": [{"id": "event.42", "address": "1AA5:0312",
                            "text": "..."}, ...]}
    story/events.json      the event script as typed records (id, class, conditions,
                           actions), not bytes
    story/names.json       planets, pilots, mech display names, House contract names
    story/pilots.json      pilot definitions: portrait id, starting skills, text ids
    story/planets.json     planet records: house, tier, position, text ids; the
                           story-planet pools
    story/music.json       the sequence table and the AdLib instruments

`import.json` is written last, so an interrupted import counts as missing.
The game re-imports when it is missing, when `import_version` differs, or
when `table_sha256` (a hash of the import table) differs, so a piece added
to the table imports into an older folder without a version bump. A
`--text FILE` override of the same shape replaces any id, for a translation
or a rewrite. Text keeps the original's control codes as `\u00NN`.

**The import table** (`src/Import/import_table.cpp`, in the repo): for each
piece, its id, exe, `SEG:OFF`, length and the first 16 hex digits of its
SHA-256. The repo ships the table, never the bytes. A player's copy is
accepted piece by piece: every piece's hash must match, and a refusal names
the pieces. Revisions are rows of segment bases, as
`src/Support/CombatInstallation.cpp` already keeps for BTECH (the
1990-01-22 BTECH has the reference layout 0x11 paragraphs later); MW_MAIN
and MW get the same table. Unknown revisions: the MSC runtime banner at
DS:0008 finds the data segment, then each piece must still match its hash.

## 3. The order (slices, each on its own branch, traces 7 of 7 or noted)

1. **Dropped.** Copy protection, disk prompts, the DOS launcher path. The
   original's run.py check covers the screens around them. Done: 19 of the
   26 are gone. MWSNAP skips the original's protection in memory (081B:16A4
   jumps to 181A), so both start a campaign alike; dropping it moves the
   random sequence, and the goldens were re-recorded. Seven stay for now:
   the launcher's file names and identity bytes and `combatExecutableFilename`
   (slice 6), `launcherMemoryTier` and `launcherExitCode` (the four-pilot
   roster, the save format and the combat hand-off read them), and
   `herculesDisplayRowOffsets` (the EGA span code reads past its own row
   table into it).
2. **The story file.** `Original/Memory` becomes the importer: it reads the
   exes once, writes `story/`, and the game's importers read `story/`
   instead. Traces equal (same content, new route). In pieces, each on its
   own branch: 2a the machinery and the intro's 14 captions, 2b the rest of
   the narrative text, 2c names, 2d `pilots.json` and `planets.json`, 2e
   `events.json` and the 1AA5 text bank, 2f `music.json`. 2a: the JSON reader
   and writer and SHA-256 (`src/Support`, from Inception's), the import table
   (`src/Import/pieces.txt` → `tools/import/make_import_table.py` →
   `import_table.cpp`), `story/text.json` and `story/import.json`, re-import
   when missing or outdated; the captions read from the story file, their
   positions still from the exe. Unit tests `json_test`, `story_test` (ctest).
   2b: the intro's ten narration lines, the deployment, after-action,
   settlement and Dark Wing texts, the contract office's narrative and house
   refusal (25 pieces; each buffer is filled whole, the rest zeroed, as the
   exe holds it). The mission descriptions (1090:8A69) mix rule headers with
   their text and saves keep offsets into them; they wait for 2d.
   2c: MW_MAIN's names (the houses' in the contract office, the units' in
   the shop and elsewhere, the new campaign's commander; 28 pieces), keyed
   by HOUSE_* and CampaignUnitKind. BTECH's names (the mech templates, the
   pilots, the default commander) need BTECH.EXE unpacked first (EXEPACK,
   `BtechDecodeInstallationImage`); they come with the importer's BTECH
   support.
3. **Rules and the new campaign** into `data/rules/`. Traces equal (same
   numbers). The importer's piece hashes check them against the exe.
4. **Layout** into `data/ui/`. Traces equal.
5. **UI words** into `data/text/interface.json`, screen by screen, in our
   wording. Each slice re-records its snaps with the changed words listed.
6. **No exe at play time.** The game starts from `story/` and `data/` alone;
   only the importer opens an exe. A test runs the traces with the exes
   moved away after import.

Each slice: no goto in new code, C++20, every function keeps its original
`SEG:OFF` in its comment, no names in the repo, headless and one suite at a
time.
