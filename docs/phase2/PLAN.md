# Phase 2: content out

The goal: the game reads no executable at play time. The original's creative
content comes from a story file the game writes once from the player's own
exes; everything else it needs is ours, in data files in this repo, or is
code. Copy protection, disk prompts and the DOS launcher go. Traces stay 7
of 7, except where our own wording changes a screen, and every such snap is
re-recorded and noted in the same commit.

The scoping report (mw3-re, `mw1/research/original-rebuild-scoping.md`,
sections 3, 4 and 7) is the brief. `INVENTORY.md` lists every item
`src/Original/Memory` holds today with its group (generated by
`tools/phase2/inventory.py`; names and native offsets only).

## 2. The file formats

Both follow Inception's shape (crescent-hawks-rebuild `docs/import.md`):
plain JSON with named fields, one place for every ID, readable and moddable.

**Ours, in the repo** (`data/`, installed beside the program):

    data/text/interface.json   {"texts": [{"id": "market.buy", "text": "Buy"}, ...]}
    data/ui/campaign.json      {"panels": {"market.list": {"x": 8, "y": 24, "width": 200,
                                 "lines": 13, "border": 1, "spacing": 2, "background": 7}},
                                "menus": {"hub": [{"x": .., "y": .., "picture": 1,
                                 "links": [5, 1, 255, 3], "text": "hub.contracts"}]}}
    data/rules/market.json     {"unit_base_prices": [...], "price_tier_multipliers": [...]}
    data/rules/new_campaign.json  {"funds": ..., "year": ..., "house_standings": [...]}

Text ids are dotted (`screen.item`). A menu row's label is a text id, not a
string. Arrays keep the original's order and length, so an index means what
it meant in the exe; each array's length is checked at load.

**Extracted, in the player's data folder** (`<write dir>/story/`):

    story/import.json      {"import_version": 1, "sources": {"MW_MAIN.EXE": "<sha256>",
                            "BTECH.EXE": "<sha256>", "MW.EXE": "<sha256>"},
                            "revision": "1990-01-22", "table_sha256": "..."}
    story/text.json        {"texts": [{"id": "event.42", "address": "1AA5:0312",
                            "text": "..."}, ...]}
    story/events.json      the event script as typed records (id, class, conditions,
                           actions), not bytes
    story/names.json       planets, pilots, mech display names, House contract names
    story/pilots.json      pilot definitions: portrait id, starting skills, text ids
    story/planets.json     planet records: house, tier, position, text ids
    story/missions.json    mission descriptions: scenario, text id; the categories
    story/music.json       BTECH's AdLib default instruments

`import.json` is written last, so an interrupted import counts as missing.
The game re-imports when it is missing, when `import_version` differs, or
when `table_sha256` (a hash of the import table) differs, so a piece added
to the table imports into an older folder without a version bump. A
`--text FILE` override of the same shape replaces any id, for a translation
or a rewrite. Text keeps the original's control codes as `\u00NN`.

**The import table** (`src/Import/import_table.cpp`, in the repo): for each
piece, its id, exe, `SEG:OFF`, length and the first 16 hex digits of its
SHA-256. The repo ships the table, never the bytes. A player's copy is
accepted piece by piece: every piece's hash must match, and a refusal names
the pieces. Revisions are rows of segment bases, as
`src/Support/CombatInstallation.cpp` already keeps for BTECH (the
1990-01-22 BTECH has the reference layout 0x11 paragraphs later); MW_MAIN
and MW get the same table. Unknown revisions: the MSC runtime banner at
DS:0008 finds the data segment, then each piece must still match its hash.

## 3. The order (slices, each on its own branch, traces 7 of 7 or noted)

1. **Dropped.** Copy protection, disk prompts, the DOS launcher path. The
   original's run.py check covers the screens around them. Done: 19 of the
   26 are gone. MWSNAP skips the original's protection in memory (081B:16A4
   jumps to 181A), so both start a campaign alike; dropping it moves the
   random sequence, and the goldens were re-recorded. Seven stay for now:
   the launcher's file names and identity bytes and `combatExecutableFilename`
   (slice 6), `launcherMemoryTier` and `launcherExitCode` (the four-pilot
   roster, the save format and the combat hand-off read them), and
   `herculesDisplayRowOffsets` (the EGA span code reads past its own row
   table into it).
2. **The story file.** `Original/Memory` becomes the importer: it reads the
   exes once, writes `story/`, and the game's importers read `story/`
   instead. Traces equal (same content, new route). In pieces, each on its
   own branch: 2a the machinery and the intro's 14 captions, 2b the rest of
   the narrative text, 2c names, 2d `pilots.json` and `planets.json`, 2e
   `events.json` and the 1AA5 text bank, 2f `music.json`. 2a: the JSON reader
   and writer and SHA-256 (`src/Support`, from Inception's), the import table
   (`src/Import/pieces.txt` → `tools/import/make_import_table.py` →
   `import_table.cpp`), `story/text.json` and `story/import.json`, re-import
   when missing or outdated; the captions read from the story file, their
   positions still from the exe. Unit tests `json_test`, `story_test` (ctest).
   2b: the intro's ten narration lines, the deployment, after-action,
   settlement and Dark Wing texts, the contract office's narrative and house
   refusal (25 pieces; each buffer is filled whole, the rest zeroed, as the
   exe holds it). The mission descriptions (1090:8A69) mix rule headers with
   their text and saves keep offsets into them; they wait for 2d.
   2c: MW_MAIN's names (the houses' in the contract office, the units' in
   the shop and elsewhere, the new campaign's commander; 28 pieces), keyed
   by HOUSE_* and CampaignUnitKind. BTECH's names (the mech templates, the
   pilots, the default commander) need BTECH.EXE unpacked first (EXEPACK);
   2c-2 brings them. 2c-2: the decoder moved to `src/Support/BtechImage.cpp`
   (no goto), and `BtechDecodeImage` leaves `btechLoadedRevision` alone. The
   importer reads BTECH's pieces in the unpacked image, rebased into the
   reference layout and loaded at 0810, so one table and one code path serve
   both revisions; `tools/import/btech_image` pipes that image to
   make_import_table.py (no second decoder). 52 pieces: the 8 mech templates,
   the 43 pilots (each written at its directory offset in its own record)
   and the default commander. `btech_revisions_test` imports both revisions
   and compares their texts (skipped without the player's files).
   2d: `story/pilots.json`, `planets.json` and `missions.json`
   (`src/Import/Records.*`): typed records whose texts are text ids. The
   importer writes them from Bytes pieces (the headers, and the offset
   tables turned into ids); the game rebuilds the original's storage and
   offset tables from them, laid out as the exe lays them out (on the
   1990-01-22 copy every byte and offset is equal). 42 pilots (portrait,
   gunnery, piloting, name, dialogue), 146 planets (the 10-byte header, name,
   description; the travel screen's alphabetical order), 34 mission
   descriptions (scenario, a second byte, text; the five categories as runs
   of ids). Saves keep mission description offsets, so a story whose texts
   change length moves them; the save format should keep ids (slice 6).
   The story-planet pools (`eventPlanetChoicePool*`,
   `campaignEventPlanetSelectors`) go with the events in 2e.
   2e, the text bank: `story/event_text.json`, MW_MAIN 1AA5's records in
   the exe's storage order, each with its directory entry and its pages
   ([FF] marker, format, rows, text id). One record (834 bytes at B1EF) no
   directory entry reaches; it is kept, unreferenced, so the bank is the
   exe's byte for byte. The game rebuilds the bank and its directory at start
   and on every EXEC (which restores the planet names events write into it)
   instead of reading the exe.
   2e, the script: `story/events.json` (`src/Import/Events.*`): the 28
   choice captions (colour, original address, text id), the 117 events in
   the order the original importer meets them (id, class, a script of 203
   commands alternating condition and action with named operands, choices
   naming captions and events), the list entries, the six lists, the fixed
   event and the six story-planet pools. The importer decodes 1090:5CF4..655C
   as the game did; the game fills its typed owners from the file. The choice
   menus are layout (slice 4) and still come from the exe; they find their
   captions by the original address the file keeps.
   2f, `story/music.json` (`src/Import/Music.*`): BTECH's eight AdLib default
   instruments (304E:2BA0), each the 13 operator parameters by name, in
   BTECH's order. The 14th byte of each row is never read and is zero; the
   importer refuses a row where it isn't, so the rebuild stays exact. The
   combat loader fills `combatAdlibDefaultInstruments` from the file. BTECH's
   sequence table (304E:7D8A) is uninitialised data filled from MUS:INF, and
   MW_MAIN's instruments (28BE:064E) are zero in the exe, so neither is
   imported.
   2g, left over: two story items are still read straight from the exe.
   `missionTitleText` (BTECH 304E:09F0..0D8B, the briefing's mission titles,
   reached through the offset table at 0DD2) becomes text ids and a list of
   titles; `contractOfficePlanetGroupStorage` (MW_MAIN 1090:4B8A..4BF0, each
   House's contract-office planets as planet selectors, FF between groups and
   FE at the end, reached through 4B80) becomes lists of planet ids in
   `planets.json`, like the story-planet pools in 2e. Both are the story's
   content, not layout or words, so 2g moves them before slice 6.
3. **Rules and the new campaign** into `data/rules/`. Traces equal (same
   numbers). The rule table's hashes check them against the exe. The plan
   is section 5.
4. **Layout** into `data/ui/`. Traces equal. The plan is section 6.
5. **UI words** into `data/text/interface.json`, screen by screen, in our
   wording. Each slice re-records its snaps with the changed words listed.
6. **No exe at play time.** The game starts from `story/` and `data/` alone;
   only the importer opens an exe. A test runs the traces with the exes
   moved away after import.

Each slice: no goto in new code, C++20, every function keeps its original
`SEG:OFF` in its comment, no names in the repo, headless and one suite at a
time.

### 5.2 The files

Plain JSON, named fields, every length checked at load, read strictly (the
story's `StrictReader` moves to `src/Support` and is shared). Proposed
shape:

    units.json      {"units": {"locust": {"tonnage", "base_price", "display": {"tonnage",
                     "speed_kph", "jump_metres"}, "heat_sinks", "weapons", "ammo_groups",
                     "jump_jet_groups", "condition_fields", "force_weight",
                     "body_repair_price", "ammo_profile": [{"family", "quantity_maximum"}],
                     "weapon_repair_prices": [...]}, ...}, "condition_score_divisors": [...]}
    market.json     {"price_tier_multipliers": [4], "ammunition_prices": {family: price},
                     "stock_kind_ranges": [{"start", "maximum"}], "freight_rates": {family: rate},
                     "start": {...}}
    repair.json     {"system_prices": {system: {kind: price}}, "attempt_failures": {...},
                     "success_roll_limits": [4]}
    houses.json     {"houses": {"kurita": {"advance_base_percent", "salvage_base_percent",
                     "payment_roll_bias", "payment_adjustment_percent", ..., "planets":
                     {"first", "count"}, "mission_planet_policy": [[...]],
                     "mission_type_limits": [8]}, ...}}
    contracts.json  {"deployment_units_by_scenario": [37], "pilot_wages": [8], "start": {...}}
    combat.json     damage tiers, transfers, hit location and cluster rows, range
                    modifiers, heat thresholds, objectives, continuation profiles, the
                    template/unit-kind maps, budget costs, AI offsets, "start"
    weapons.json    {"weapons": [{"damage", "ammo_family", "reload_ticks", "heat",
                     "range_class", "ranges": {"minimum", "short", "medium", "long"},
                     "critical_slots", "unknown_14", "cluster_row", "projectile_profile"}]}
    mechs.json      {"mechs": [{"name": "combat.mech_template.1.name", "tonnage", ...,
                     "armour": {...}, "internal": {...}, "mounts": [...], "ammo": [...],
                     "jump_jets": [...]}]}
    combat_assets.json  frame counts and effect resource deltas
    new_campaign.json   the save block's fields under the codec's names

- **Enumerated axes are keyed by name, not position.** House, unit kind, ammo
  family, weapon kind and body/armour location use the enum names the code
  already has (`CAMPAIGN_UNIT_LOCUST` → `"locust"`). The loader checks that
  every key is present exactly once, so a typo can't silently shift a row.
  Plain sequences (rolls, tiers, frames) stay arrays. This refines §2's
  "arrays keep the original's order": the order still exists, it just
  isn't load-bearing in the file.
- **Fields the port doesn't understand yet** keep their bytes under
  `unknown_<offset>`, and can be renamed once understood.
- **Pointer tables become references.** `unitAmmoProfiles` and
  `weaponRepairPricesByKind` become each unit's own list. The game rebuilds
  the native DS offsets where code still uses them, and the hash check
  covers the rebuilt offsets.

### 5.4 How the hashes check them

The rules don't go in `pieces.txt`: that table's hash re-imports the story,
and rules aren't story. They get a table of their own:
`src/Rules/rule_pieces.txt` uses the same row format (`id EXE SEG:OFF len`)
and is generated into `rule_table.cpp` by `make_import_table.py --rules`,
with the same parser and the same `btech_image` path. Its hashes come from
the 1990-01-22 exes. It has one piece per table, the pointer tables
included, and new_campaign is split around the commander's name.

- **`rules_test`** (ctest, no game files): loads `data/rules/`, encodes each
  table back to native bytes with the same encoders the game fills its
  owners with, and compares each table's SHA-256 prefix with the rule
  table's. A mismatch fails, naming the table. A table tuned on purpose
  later is marked `tuned` in `rule_pieces.txt`, keeping its row but dropping
  its hash, so the test lists it as ours instead of failing.
- **`rules_exe_test`** (ctest, skipped without `MW1O_GAME`, like
  `btech_revisions`): compares every piece byte for byte with the player's
  exes, both BTECH revisions.
- The game itself never opens an exe for rules and checks no hash at play
  time.

### 5.5 The machinery

- `data/` sits in the repo and is installed beside the program. The game
  finds it beside the executable (`SDL_GetBasePath()`), or wherever
  `--data DIR` points. CMake copies it beside the built binary on every
  build (Visual Studio included: it opens the folder as a CMake project,
  and `src/Build.ps1` builds through CMake), and `check.py --port` uses
  the build's copy. The old Visual Studio project files were retired.
- `src/Rules/`: typed structs, the strict loaders, encoders to native bytes,
  and C doors in `mechwarrior/rules.h` (`MwRules*`). The `Original/Memory`
  importers call the doors instead of reading `data+0x....`. The rules load
  once at start and are held in memory, so the importers that run again on
  every EXEC fill from memory, as the story doors do.

**Start values (10).** These are layout-shaped, but play writes them:
`calendarTextX`, `calendarTextY`, `calendarBackground` and
`calendarForeground` (1090:117E), `pilotCardTextX` (243C),
`crewScreenRightEdge` (2438), `contractRequestTextColour` (4B34),
`afterActionRosterRowOffset` (1229), `reserveAmmoMechColours` (3F70), and
BTECH's `lanceOrderPanelTextX` (304E:008C). 3f's method decides each one:
read the code, then perturb the value against the traces with a control.
A value that is always written before it's read becomes code, zeroed or set
where the exe reloaded it. The others become `"start"` entries in their
screen's file.

**Not layout:**
- `orderMapPositionMask` (304E:4EF0) lies past BTECH's file data, so it is
  code, zeroed like 4F32.
- The menus' past-end probes (`*NavigationProbe`, and the
  `sentinelEnabled` pointers into neighbouring objects) copy the original
  reading one byte past a menu. They stay code as they are: several point
  at state that play changes, so a fixed value in a file would differ.
- The 103 layout enumerators in the headers (`REPAIR_DONE_X` and the like)
  are the exe's code immediates, not data. They stay code. A later change
  can move them into data/ui by name.

### 6.2 The files

Plain JSON, read strictly with `StrictReader`, one file per screen family:

    hub.json        the three hub menus, the calendar, the notification boxes
    crew.json       company, commander profile, crew, bar, recruit, the pilot card
    complex.json    Mech Complex, owned list, service, repair, the body diagrams
    dealer.json     the market lists, detail panels, reserve ammunition
    contract_office.json  the two panels and menus, the term and date positions
    travel.json     the travel panels and menus, the transport frames
    options.json    options, restore, confirmation, news
    events.json     the two choice menus
    cockpit.json    BTECH: layouts, diagrams, HUD colour schemes, landscape rows, fonts
    orders.json     BTECH: the lance order panel's rows, deltas and colours

Shapes:

    caption  {"at": [x, y], "colour": c}
    panel    {"at": [x, y], "width", "bottom_inset", "border", "line_spacing",
              "background", "lines": ["<caption id>", ...]}
    menu     {"records": [{"enabled", "text_record", "at": [x, y],
              "action": "continue.mech_complex" | null, "picture",
              "up", "down", "left", "right"}]}

- **Captions are keyed by our ids** (`complex.repair.title`, for example).
  The same ids name their words in slice 5. Until slice 5, the loader takes
  each caption's text from the exe at the native offset that the piece
  table gives for that id.
- **Panels name their lines by caption id.** The line count is the length
  of the list, and the encoder rebuilds the native pointers from the
  captions' offsets, as slice 3 did for its pointer tables.
- **Menu links are record indices within the menu**, or null for the
  original's FF. The loader refuses a link that is out of range, or one
  that leads into a different menu than the exe's structure allows: bad
  layout data fails at load, never jumps somewhere odd. **Actions are names** from `MwCampaignContinuation`
  (`CAMPAIGN_CONTINUE_MECH_COMPLEX` → `"continue.mech_complex"`); an unknown
  name is refused. The event menus name a caption id instead of a picture.
- **Keyed axes use the code's enums**, as in slice 3: armour locations, unit
  kinds and templates key the diagrams, the per-kind tables and
  `mechCockpitLayoutIndices`. A cockpit layout's fields use the
  `BtechCockpitLayout` and `BtechHudColourScheme` member names, and
  unnamed fields keep `unknown_<offset>`.
- **Pointer tables become references:** the body diagram per unit kind
  (null for none), the six reserve ammunition compatibility panels, and the
  pilot assignment captions.
- data/ui holds numbers and our own names only, never exe text.

### 6.3 What may change, and what must stay exact

In slice 4, every number keeps the exe's value, so the traces stay equal and
the hashes prove it. After slice 4:
- **Tunable:**
  - positions, sizes and spacing;
  - borders and backgrounds;
  - colours: captions, HUD schemes, lamps, body damage fills, order
    conditions;
  - cockpit rectangles and gauge anchors;
  - the bitmap placements' x and y;
  - menu links, provided every link stays in range (the loader checks).
- **Fixed by contract:**
  - **Line and record counts:** the code indexes the lines and records by
    number, and the importers check the counts today.
  - **Actions:** the code dispatches on them.
  - **The install's art and fonts:** picture indices, the animation and
    transport frames, the bitmap indices in cockpit placements, the font
    widths and heights, and the landscape camera rows' palette slots. These
    describe the install's files, like combat_assets.json.
  - **`mechCockpitLayoutIndices`:** it maps templates to layouts, so
    change it only together with the layouts.
- **Tied to words (slice 5):** `calendarMonthNameWidths`,
  `repairTitleLeadingSpacesByKind` and `contractDateYearXOffsets` measure
  or pad particular texts. Slice 5 should derive them from the words (and
  `pilotCardColumnOrigins` if that proves to be text-bound too) rather
  than tune them separately.
- **Code still draws some things itself:** a moved panel doesn't move what
  code places by immediates (6.1). The file says this in a note beside the
  affected screens.

### 6.4 How the hashes check them

This is slice 3's scheme with a table of its own. `src/Ui/ui_pieces.txt`
uses the same row format, `make_import_table.py --ui` turns it into
`ui_table.cpp`, and the same `btech_image` path serves both BTECH
revisions. There is one piece per:
- panel: its header and line pointers;
- menu: all of its records;
- caption head: 5 bytes, with the text excluded;
- table, as listed in 6.1.

That is roughly 35 + 30 + 230 + 25 pieces. A caption piece's offset is
also where that caption's text starts, 5 bytes later, until slice 5.

- **`ui_test`** (ctest, no game files): loads `data/ui/`, encodes each
  piece back to native bytes and compares hash prefixes, naming any piece
  that differs. A piece tuned on purpose is marked `tuned`, as in rules.
- **`ui_exe_test`** (ctest, skipped without `MW1O_GAME`): compares every
  piece byte for byte with the player's exes, in both BTECH revisions.
- The game opens no exe for layout and checks no hash at play time.

### 6.5 The machinery

- `src/Ui/` mirrors `src/Rules/`: typed structs, strict loaders, encoders to
  native bytes, and C doors in `mechwarrior/ui_layout.h`
  (`MwUiCopyNative`, `MwUiCopyWords`, `MwUiCopyBytes`, and
  `MwUiCaptionOffset` for the text lookup until slice 5). These are not
  copies of the rules code. The piece lookup, `piece_range`, the hashing
  and `StrictReader` move to `src/Support` and serve both. data/ui is
  installed and found beside data/rules.
- The importers keep their shape. A panel read becomes one door call into
  the same `MwPanelDescriptor`, and a menu read fills the same `MwUiRecord`
  array. The runtime code doesn't change.
- The inventory learns the `ui` door, as it learned the rule door in 3f.
